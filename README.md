# Batched Sequential Execution (BSE)

[![tests](https://github.com/tuckerebc-max/batched-sequential-execution/actions/workflows/test.yml/badge.svg)](https://github.com/tuckerebc-max/batched-sequential-execution/actions/workflows/test.yml)

A model does its best work inside a band — roughly 600-1,500 words of finished
prose, a handful of slides, one vertical slice of code. Ask for more than that
in one pass and quality does not plateau, it decays: fidelity to the brief
slips, earlier mistakes make later ones likelier, and a bigger context window
does not fix it. The fix is not a bigger pass. It is a sequence of passes that
each stay inside the band, each get verified against something external before
they count, and get stitched together afterward into one coherent whole.

## What this repo is

A single portable skill (`SKILL.md`, drop into any Claude Code, Cowork, or
claude.ai skills directory) plus a zero-dependency Python CLI
(`scripts/bse.py`) that does the bookkeeping the skill relies on: scaffolding
the run directory, validating the plan, assembling briefs, running mechanical
checks, and refusing to record work that hasn't passed them.

## How it works

Seven moves, always in this order:

1. **CHARTER** — write the contract once: goal, through-line, audience,
   voice, terminology lock, sources, acceptance criteria. One page. Every
   batch reads it.
2. **PLAN** — decompose into ordered, typed, budgeted, verifiable units. This
   is where quality is decided; validate it and show it to the user before
   executing anything.
3. **BRIEF** — assemble exactly what one executor needs: charter + this
   unit's spec + the carried baton + named input slices. Nothing else.
4. **EXECUTE** — one unit, fresh context, output written to a file.
5. **VERIFY** — mechanical checks first (`bse.py check`), then, for units that
   declare judgment predicates, a reviewer bound to the brief and recorded
   with `bse.py review`. The model's own satisfaction is never the halting
   condition.
6. **RECORD** — only predicate-passing work enters the ledger. The tool
   refuses to mark a unit done on a failed/missing check or a missing/failing
   review.
7. **STITCH, then SEAM** — `bse.py stitch` assembles the verified units in
   plan order into `draft.md`; a real editing pass then repairs the seams and
   writes the front and back matter last (only now do they have something to
   summarize) into `final.md` — by hand, never by the tool.

All of it lives in files, not the conversation:

```
.bse/<run-id>/
  CHARTER.md      the contract: goal, through-line, audience, voice,
                  non-negotiables, terminology lock, sources, acceptance
                  criteria. <= 1 page.
  PLAN.md         ordered units, each with a budget, inputs, intent,
                  what it produces, its verification predicates, done_when.
  LEDGER.md       append-only progress log. First line is the identity header.
  ledger.json     machine mirror (authoritative for tooling)
  carry.md        the baton: <= 400 words handed forward to the next unit
  briefs/<ID>.md  the self-contained brief one executor receives
  batches/<ID>.md the output of one unit (lightweight markdown)
  reports/<ID>.md its verification report
  front-matter.md introduction / executive summary — written in the seam pass
  back-matter.md  conclusion — written in the seam pass
  draft.md        mechanical assembly (regenerated by `stitch`; never hand-edited)
  final.md        the seam-passed deliverable — written by hand, never by the tool
```

Resume rule, verbatim from `SKILL.md`: read `LEDGER.md`. If its first line
names this run's charter, every unit with a `done` line is complete — do not
re-execute it. Resume at the first unit without one.

## Quickstart

```bash
# 1. scaffold a run directory
python scripts/bse.py init --run-id demo --title "Demo Report" --total 20000w

# 2. edit .bse/demo/CHARTER.md and PLAN.md (replace the SAMPLE unit),
#    then validate the plan
python scripts/bse.py plan --validate

# 3. see progress and what's next
python scripts/bse.py status
python scripts/bse.py next

# 4. for the returned unit ID: assemble its brief, dispatch an executor
#    against the brief file (it writes batches/ID.md), then verify and record
python scripts/bse.py brief B001
python scripts/bse.py check B001
#    a unit declaring source:/charter: judgment predicates additionally
#    needs a reviewer verdict before it can be recorded done:
python scripts/bse.py review B001 --verdict pass --report reports/B001-review.md
python scripts/bse.py record B001 --status done --artifact batches/B001.md

# 5. repeat step 4 (next -> brief -> execute -> check [-> review] -> record)
#    until done, updating the baton before each record
python scripts/bse.py record B002 --status done --carry carry_update.md

# 6. once every unit is recorded, assemble the mechanical draft
python scripts/bse.py stitch

# 7. seam pass: read draft.md against the charter's through-line, repair the
#    seams reports/stitch.md flags, then write front-matter.md, back-matter.md,
#    and final.md by hand — `stitch` refuses to write final.md itself

# 8. check the whole run for drift between the ledger and the filesystem
python scripts/bse.py audit
```

Every command accepts `--run-dir PATH` and `--json`; run
`python scripts/bse.py --help` (or `<command> --help`) for the full contract.
Exit codes: 0 success, 1 validation/verification failure, 2 usage error.

## Light mode

Below roughly 12 units, the run directory and tooling above are more
machinery than most jobs need. Light mode keeps the part that matters most —
a numbered outline with a word budget per item, one pass per item, a
five-line note carried forward between them — and drops the rest: no
`.bse/`, no ledger, no external predicate beyond word count and a
terminology check done by eye. It has a real limit worth knowing before you
pick it: nothing stops a model from claiming an item is finished when it
isn't, the way `bse.py record` does. See
[`references/light-mode.md`](references/light-mode.md) for the loop, a
worked six-unit example, and exactly when to escalate to full mode instead.

## Installation

**(a) Clone as a skill directory.** Drop this repo at
`~/.claude/skills/batched-sequential-execution/` (user-wide) or
`.claude/skills/batched-sequential-execution/` inside a project. The root
`SKILL.md` is the skill; nothing else to configure.

**(b) Install as a Claude Code plugin, from a marketplace.**

```
/plugin marketplace add tuckerebc-max/batched-sequential-execution
/plugin install batched-sequential-execution
```

**(c) Upload as a skill in claude.ai or Cowork.** Zip or upload the repo
folder directly through the skills UI — `SKILL.md` at the root is what gets
picked up.

The CLI needs Python 3.9+ and nothing else — no `pip install`, no lockfile.
If Python is unavailable in the environment, the skill degrades gracefully:
run the same seven-move loop by hand against the same markdown files. The
tool is bookkeeping, not the discipline; it just makes the discipline cheap
to keep.

## Design principles

Ten commitments, each traced to a source in
[`references/evidence.md`](references/evidence.md):

1. Plan granularity is the dominant quality lever — deeper plans beat better drafting.
2. Every unit carries an explicit budget — a control signal, not a suggestion.
3. Serial with a passed baton beats parallel fan-out; parallel is allowed only with a mandatory reconciliation pass.
4. Curated context, not accumulated transcript — prior batches in full are distractors, not free information.
5. Every verification binds to an external, checkable predicate — the model's own satisfaction is never the halting condition.
6. Only verified work enters persistent state.
7. State lives in files, not in the conversation — compaction destroys conversational memory.
8. Per-step accuracy decays, it does not merely compound — fresh context per unit is the mitigation.
9. Decomposition is allowed at execution time — a unit that discovers it is too big should split, not push through.
10. Type your units — telling the executor what kind of operation it is doing matters as much as the decomposition itself.

## What it is not

- **Not a task manager.** It has no notion of people, deadlines, or projects
  — only units, budgets, and a ledger for one run.
- **Not a content authority.** It doesn't decide what good prose, a good
  slide, or a good diff looks like. A domain skill (or the user) owns voice
  and standards; this skill owns sequencing, budgets, and verification.
- **Not useful below five units.** If a deliverable decomposes into fewer
  than five units, this is overhead — do the work directly and say so.

## Credits

This design borrows deliberately from field-tested harnesses and published
research rather than inventing a pattern from scratch. See
[`references/evidence.md`](references/evidence.md) for the full trace;
in brief:

- **[obra/superpowers](https://github.com/obra/superpowers)** —
  the ledger with an identity header and the resume-rule pattern (read the
  ledger, treat what it marks done as done, resume at the first gap); the
  "never pass a subagent" list; artifacts passed as file paths; explicit
  model tiering; capped fix rounds.
- **[github/spec-kit](https://github.com/github/spec-kit)** — a task-line
  schema derived from spec-kit's (`- [ ] T001 [P] description`), IDs
  sequential in execution order, `[P]` reserved for genuinely independent
  units, a write-back checkbox as the resume marker, halt-on-failure.
- **[AMAP-ML/LongHorizon-Harness](https://github.com/AMAP-ML/LongHorizon-Harness)**
  — the load-bearing invariant that only independently verified results enter
  persistent task state, and the Manager/Executor/Auditor separation.
- **[THUDM/LongWriter](https://github.com/THUDM/LongWriter)** (its AgentWrite
  harness) — word budgets attached to each plan item, the chunk-size band,
  and the instruction that a chunk must never write a conclusion because the
  work is ongoing.
- **[stanford-oval/storm](https://github.com/stanford-oval/storm)** —
  per-unit retrieval slices with a hard cap, parallel sections paid for with
  a deduplication pass, and the lead section generated last.
- Anthropic's
  **[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)**
  and
  **[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)**
  — the run directory as durable state outside the context window, the
  one-feature-at-a-time discipline, and the naming of one-shotting and false
  victory as failure modes to guard against explicitly.
