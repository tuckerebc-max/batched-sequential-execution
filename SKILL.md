# Batched sequential execution

A model does its best work inside a band — for prose, somewhere around 800–1,200
words of finished text per pass; for slides, a handful; for code, one vertical
slice. Past that band, accuracy, fidelity to the brief, and faithfulness to the
goal decay together, and the decay compounds: errors already in context make
further errors likelier. (The band is a calibrated default, not a measured
constant — see [evidence](references/evidence.md).)

This skill does not ask for a bigger pass. It makes the big job a sequence of
in-band passes, each verified against an external predicate before it counts,
each recorded in a file that survives compaction, and all of them assembled at
the end into a single artifact that reads as one thing.

**The contract: nothing is "done" because the model says so. A unit is done when
a predicate says so, and the ledger — not the conversation — is what remembers.**

## Two modes. Choose before you build anything.

**Light mode** — half a page of charter, a numbered outline with a word budget
per item, one pass per item, a five-line note handed forward, a plain list of
what is finished, and one seam pass at the end. No run directory, no validator,
no subagents. Most of the benefit, a twentieth of the machinery.
See [light mode](references/light-mode.md).

**Full mode** — everything below. Escalate to it when any of these is true:

- the run will span sessions, days, or a context reset
- it exceeds roughly 12 units
- more than one agent will touch it
- the result must be auditable — someone will ask how a claim got there
- the work is going to a client, a board, or publication

Below five units, neither mode applies. Say so and do the work directly.

## When NOT to use this

- The job decomposes into fewer than five units.
- The work is one indivisible judgment (a decision memo, one tricky function).
- The user wants a fast rough draft, not a faithful one. Batching buys fidelity
  and costs wall-clock time. Name the trade before choosing it.

## The state model

Everything lives in files. The conversation is scratch; the run directory is truth.

```
.bse/<run-id>/
  CHARTER.md       the contract: goal, through-line, audience, voice,
                   non-negotiables, terminology lock, sources, acceptance
                   criteria. <= 1 page. Read by EVERY batch.
  PLAN.md          ordered units: budget, type, inputs, intent, produces,
                   verification predicates, done_when
  LEDGER.md        append-only progress log; first line is the identity header
  ledger.json      machine mirror (authoritative for tooling)
  carry.md         the baton: <= 400 words handed forward to the next unit
  briefs/<ID>.md   the self-contained brief one executor receives
  batches/<ID>.md  the output of one unit (lightweight markdown)
  reports/<ID>.md  its verification report
  front-matter.md  introduction / executive summary — written in the seam pass
  back-matter.md   conclusion — written in the seam pass
  draft.md         mechanical assembly, regenerated by stitch, never hand-edited
  final.md         the seam-passed deliverable. This is the output.
```

`draft.md` is machine output and is overwritten on every stitch. `final.md` is
the thing you ship. Never edit `draft.md`; never regenerate `final.md` by
stitching.

Artifacts move **as file paths, never as pasted text**. Pasting a batch back into
the conversation defeats the design.

## The loop

INIT → CHARTER → PLAN → [ BRIEF → EXECUTE → VERIFY → RECORD ] × N → STITCH → SEAM

### 0. INIT

`bse.py init --run-id <id> --title "<title>" --total <n><unit>` scaffolds the run
directory. Do this before writing anything. The charter's total may name more than
one denomination (`--total "20000w, 40slides"`).

### 1. CHARTER — write the contract

Ask only the questions needed to make every acceptance criterion testable: what
is the finished thing, who reads it, what must be true of it, what is out of
scope, which sources are authoritative, which terms must be used exactly.

Two fields earn their keep above all others:

- **Through-line** — one sentence stating what the finished thing argues or
  establishes. It goes verbatim into every brief. A document written in seventeen
  blind pieces can be locally flawless and collectively say nothing; the
  through-line is the only defense, and it is not repairable at the seam.
- **Terminology lock** — a short table of wrong form → approved form. It becomes
  a mechanical verifier for free.

**When the charter depends on research you have not done yet** — a survey, a
landscape scan, "find out and then recommend" — do not guess. Write charter v0
with a provisional terminology lock, plan only the research units, run them,
then amend the charter, record a `RULING` saying what changed and why, and plan
the remainder. This is a named path, not a failure.

### 2. PLAN — this is where quality is decided

Deeper plans beat better drafting. Spend real effort here.

Each unit gets: an ID in execution order; a **type** (`research | compose |
revise | transform | verify | assemble`); an explicit **budget**; its **input
slices** (specific paths and line ranges, never "the repo" or "the sources"); a
one-paragraph **intent** a stranger could act on; what it **produces** that later
units may rely on; its **verification predicates**; and a binary **done_when**.

Then `bse.py plan --validate`, and show the user the plan before executing. This
is the normal path's only approval gate. Do not begin a seventeen-unit run on an
unreviewed plan.

Placeholders are forbidden in a plan: no "TBD", no "etc.", no "similar to the
section above". A unit that cannot be specified cannot be verified.

The validator enforces predicate adequacy — a word-budgeted unit must declare
`word_count`, a unit reading named sources must declare `citation_tags` or a
source predicate, a non-final `compose` unit must declare `no_conclusion`. Treat
its complaints as design feedback, not as obstacles.

### 3. BRIEF — assemble exactly what one executor needs

`bse.py brief <ID>` writes the charter + this unit's spec block + the current
carry + the named input slices. Nothing else.

**Never pass an executor:** the full plan; other batches' text; the conversation
history; accumulated summaries of prior work; pre-judgments about what the
reviewer should overlook. Each is a distractor that measurably degrades output,
not free context.

### 4. EXECUTE — one unit, fresh context

Preferred: dispatch a subagent with the **brief file path**; it writes
`batches/<ID>.md` itself. Inline execution is fine for short runs if context is
cleared between units.

Standing instructions to every executor:

- Produce only this unit. Do not write ahead or summarize what came before.
- Hit the budget within ±15%. The budget is a control signal, not a suggestion.
- **Write no concluding, summarizing, or valedictory language** — the work is
  ongoing, and a chunk that wraps itself up cannot be stitched.
- Do not restate anything in the carry's "do not repeat".
- If the unit is too large to do well, stop and say so. Splitting is correct;
  a rushed oversized batch is not.

### 5. VERIFY — bind every check to something external

Two halves, and **both are gates**:

- **Mechanical** — `bse.py check <ID>`: budget adherence, required headings,
  no placeholders, terminology conformance, citation tags, no premature
  conclusion, tests pass, schema valid.
- **Judgment** — source fidelity and charter compliance, decided by a reviewer
  pass whose prompt contains **only** the brief, the artifact, and the
  predicates. Record its verdict with `bse.py review <ID> --verdict pass|fail
  --report <path>`. A unit that declares judgment predicates cannot be recorded
  done until that verdict exists and passes.

Unanchored self-critique is worse than no critique: a model reviewing its own
prose against nothing but its own taste can make the work worse. Every check must
name something checkable, and the halting condition must never be the model's own
satisfaction.

On failure: at most **3 fix rounds**, then split the unit or mark it blocked and
surface it. A budget shortfall is the exception that permits new drafting; every
other fix is the smallest change that clears the finding.

### 6. RECORD — only verified work enters state

1. Write the next baton with the carry-update prompt
   ([prompts](references/prompts.md)) — the carry does **not** maintain itself,
   and a stale carry is the most common silent failure in this loop.
2. `bse.py record <ID> --status done --carry <file>`.

The tool refuses `done` when mechanical checks failed, were never run, or a
declared judgment predicate has no passing review. That refusal is the feature.

Then report one line: `B004 done (1,240w, 4/4 checks, review pass) — 4 of 17
units`. Deliver the interim markdown alongside it when the user is following
along. A batch should land every 5–10 minutes of agent work.

### 7. STITCH, then SEAM

`bse.py stitch` assembles in plan order into `draft.md` and reports duplicates,
terminology violations, budget drift, and every seam. It refuses while any unit
is incomplete unless you pass `--partial`.

Then the **seam pass**, which is a real editing pass and produces `final.md`:

0. Read the whole draft once against the charter's through-line. If the argument
   is not there, this is a re-plan, not an edit. No local repair fixes it.
1. Remove content two units both covered (the report names it).
2. Repair transitions at each boundary.
3. Enforce the terminology lock across the whole.
4. Check pronouns, antecedents, and register across boundaries.
5. **Now** write `front-matter.md` and `back-matter.md` — introduction,
   executive summary, conclusion — because only now does everything they
   summarize exist.
6. Write `final.md`.
7. Hand `final.md` to the format skill (docx, pptx, xlsx, pdf) to render.

Batches never write the final binary format. Markdown to the very end.

## Resume rule — state this verbatim, follow it exactly

> Read `LEDGER.md`. If its first line names this run's charter, then every unit
> with a `done` line is COMPLETE — do not re-execute it. Resume at the first unit
> without one.

Conversation memory does not survive compaction. Re-running finished work is the
most expensive failure in this pattern, and the ledger is the only thing that
prevents it. Run `bse.py audit` on resume: it catches units marked done whose
artifacts are missing, empty, or changed since verification.

## Batch sizing

| Unit type | Default batch | Ceiling | Shrink when |
|---|---|---|---|
| Prose, new | 800–1,200 finished words | 1,500 | dense citation, >3 sources, technical derivation |
| Prose, revision to feedback | 6–10 discrete items | 15 | items interact, or any is structural |
| Slides, created | 4–6 slides | 8 | heavy data or bespoke layout per slide |
| Slides, edited to spec | 8–12 slides | 20 | each slide needs judgment |
| Code | 1 vertical slice | ~400 changed lines | crosses module boundaries |
| Data / sheets | 1 sheet or derived table | 2 | formula chains cross sheets |
| Extraction / research | 5–8 sources | 12 | sources are long or conflict |

Rules that override the table:

- Size by **what can be verified in one predicate set**, not by what the model
  could produce.
- A unit's brief, inputs, and expected output should fit well under half the
  executor's usable context.
- Two verification failures on one unit means the unit is too big. Split it.
- Budgets should sum to within 20% of the charter's totals, per denomination.
  The validator checks this; scope grows silently otherwise.

## Modes of execution

- **solo** — one session, context cleared between units. Under ~8 units.
- **delegated** (default) — supervisor holds only plan and ledger; a fresh
  subagent per unit; a separate reviewer for judgment predicates.
- **wave** — up to 4 independent `[P]` units in parallel (`bse.py next --all`),
  followed by a **mandatory** reconciliation pass. Parallel units cannot see each
  other and will overlap and drift in register; reconciliation is the price of
  the speed. Never for prose that must flow.
- **relay** — the run spans sessions or days. Each new session bootstraps from
  the ledger identity header and assumes nothing else.

Assign models explicitly, never by inheritance: mechanical and transform units to
a fast model; compose and revise to a mid model; plan authoring, the seam pass,
final review, and any ruling to the most capable.

## Failure modes and their guards

| Failure | Guard |
|---|---|
| One-shotting — tries the whole thing at once | Plan gate; the executor receives one unit's brief |
| False victory — claims done, isn't | Only work passing mechanical checks and any declared review is recorded |
| Re-doing finished work after a context reset | Ledger identity header + resume rule |
| Drift from the charter | Charter in every brief; terminology lock as a verifier |
| Argument dissolves across units | Through-line in every brief; seam step 0 |
| Stale baton — every unit gets the same carry | Carry written before every record; `audit` flags an untouched carry |
| Seam damage — repetition, tonal breaks | Carry's "do not repeat"; stitch report; seam pass |
| Wrapping up mid-draft | Executors are forbidden concluding language |
| Thrash — endless fix rounds | Cap of 3, then split or block |
| Stall — two units with no ledger advance | Stop retrying; re-plan |
| Supervisor context bloat | Supervisor reads status and paths, never batch text |
| Silent scope growth | Budget-sum check at plan time, reported at stitch, enforced by `audit` |

## Using this inside another skill or workbench

This skill is an **execution wrapper**, not a content authority.

- The **domain skill** decides what good looks like (voice, method, standards).
- **This skill** decides how much happens at once, in what order, and what must
  be true before it counts.
- The **format skill** renders `final.md` at the very end.

To invoke it as a sub-step, hand it: the deliverable and target size, the unit
type, the authoritative sources, the acceptance criteria, the through-line, and
any house standards to copy into the charter. It returns `final.md` plus the
ledger as the audit trail of how the thing was made. If the caller already has a
plan, skip move 2 and validate theirs instead. See
[composition](references/composition.md).

## Tooling

`scripts/bse.py` — Python 3.9+, standard library only, Windows and POSIX.

```
bse.py init --run-id ID --title T --total "20000w, 40slides"
bse.py plan --validate
bse.py status
bse.py next [--all]                      --all lists every unblocked unit (wave mode)
bse.py brief ID [--out PATH]
bse.py check ID [--artifact PATH]
bse.py review ID --verdict pass|fail --report PATH
bse.py record ID --status done|fix|blocked [--artifact P] [--carry F] [--note N] [--force]
bse.py record RULING --note N [--unit ID]
bse.py carry --set FILE | --show
bse.py stitch [--out draft.md] [--partial]
bse.py audit
```

Every command takes `--run-dir` and `--json`. Run `--help` for the full surface.

The tool is deterministic bookkeeping, not a dependency: if Python is
unavailable, run the same loop by hand against the same files. The discipline is
the skill; the script only makes the discipline cheap to keep.
